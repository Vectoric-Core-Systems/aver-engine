What's inside

Everything a runtime needs. Nothing it doesn't.

Every subsystem is a module behind its own switch, with its own versioned C seam. Turn one off and the engine still builds, still runs, and still passes its headless tests.

Modular by construction

A strict dependency DAG from core up to runtime. No god object, no UObject, no reflection tax you didn't ask for — you pay only for the modules you compile in.

DirectX 12 renderer

Physically-based shading, a procedural sky, RayQuery global illumination and shadows, a mesh-shader geometry path, wireframe and line passes, and MSAA as a runtime setting — not a rebuild.

C# gameplay, hot reloaded

An in-process CoreCLR host with a collectible load context. Write actors, pawns, HUDs and materials in C#, hit Reload Scripts, and the result swaps into the running editor without a restart.

Physics you can trust

Jolt is vendored as the rigid-body backend, wrapped in the engine's own plain-C interface — so the solver is swappable and the gameplay layer never sees a third-party type.

The editor is the runtime

One executable. A docked ImGui shell composited straight over the live D3D12 viewport, with a project browser, asset and actor editors, a Details panel and one-key script compilation.

Audio down to the buffer

A Core-only mixer — voices, buses, 3D pan and distance attenuation — that fills a buffer you supply, with a WASAPI device behind a separate seam. Testable with no sound card in the machine.

Architecture

A dependency graph you can hold in your head.

Modules point one direction only. Nothing above the RHI is allowed to reach down past it, and the scripting host never meets a graphics type at all.

Layers, not spaghetti

Each module declares what it may depend on and the build enforces it. That constraint is what makes the headless tests meaningful: nine of them stand up their own mock device and assert on recorded draw calls, so correctness doesn't need a GPU.

  • One seam per module — not one flat ABI for everything, so each versions independently.
  • Core-only where possible — the UI, mixer and scene layers link nothing device-specific.
  • Compile-time switches — AVER_MODULE_* turns any optional subsystem off entirely.

core→assets→formats→render.pbr
core→scene→framework→runtime

One convention, written down

Half the pain in engine work is arguing about axes. Aver settles it once, at the top of the tree, and every module — renderer, physics, scene graph, importer — is held to it.

The same discipline applies to storage: a single AVR1 container underneath, with typed readers and writers for meshes, materials, maps and audio, plus glTF import on the way in.

  • Materials are C# source — compiled to .ocmat, so the source of truth is code you can diff.
  • Actors round-trip — drag a gizmo and the editor rewrites the placement in the actual .cs.
  • Content lives outside — the engine ships no game data; a project is a sibling folder.

Build

Two commands to a running editor.

CMake and Ninja come from the Visual Studio C++ workload. dotnet is optional — configure without it and the managed half is simply skipped.

PowerShell — repo root
# configure + build (Debug)
> ./scripts/build.ps1

# ...or Release, into a separate tree
> ./scripts/build.ps1 -Release

# build, then launch the editor
> ./scripts/run.ps1

# run with no window at all
> ./scripts/run.ps1 --headless --frames 5

# draw a HUD through the C seam
> ./scripts/run.ps1 --ui-demo

# probe frames against a recorded baseline
> ./scripts/gates.ps1 -Config baseline

Debug and Release, side by side

The two build trees coexist on purpose. Each carries its own image-gate baseline, because optimisation changes floating-point codegen — comparing one build against the other's numbers is exactly the mistake the pairing exists to prevent.

  • Standalone tests — fourteen executables land beside the editor and run directly.
  • No GPU required — the renderer tests supply their own mock device.
  • Tests ship with modules — switch a module off and its suite goes with it.
