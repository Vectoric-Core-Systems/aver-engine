Start with the honest part

The mixer is built and asserted sample by sample. The WASAPI device is built. The C seam is built, and the .ocaudio container round-trips. What hasn't happened is anyone recording a listening test.

STATUS.md puts it plainly: “No sound has been heard.” There's a build/bin/AudioProbe.exe, and AudioTest passes 70 headless assertions — but as the doc itself points out, a mixer that outputs silence would pass all seventy the same way.

So read this page as a description of a subsystem that is correct on paper and untested against a speaker. That gap is the honest state of it, and the rest of what follows is worth more with the gap stated than without.

Three targets, one hard rule

The audio stack mirrors the split the engine already uses for its UI renderer: a Core-only logic layer that never touches hardware, with a thin device layer bolted on afterwards. Aver.Audio depends on Aver.Core and nothing else, and its mix() fills a buffer the caller supplies. It never opens a device.

Aver.Audio.Wasapi is the only part that knows a sound card exists. Aver.Audio.Abi is the C seam a game calls, and it's shared and links the device rather than just the mixer — because “play a sound” only means anything once something is driving hardware.

The reasoning for building it in that order is blunt. A wrong pan law and a correct one produce the same waveform to someone reading source, and the same silence to a screenshot. Without a way to run the mixer headlessly and assert on individual samples, an audio bug is effectively unfindable by inspection. So the mixer came first, and the device second.

Constant power, and boundaries that don't pop

Panning is constant-power — l*l + r*r == 1 — so a source swept across the stereo field holds its energy instead of dipping about 3 dB in the middle the way a naive linear pan does. That's a defect the docs describe as audible while looking perfectly fine on paper, which is roughly the theme of the whole subsystem.

Distance attenuation is exactly 1.0 at or inside the inner radius and exactly 0.0 at or beyond the outer one, with no discontinuity at either boundary. The failure mode being designed against is a sound audibly popping as the listener crosses a radius.

The listener is nine atomics rather than a struct behind a lock: written once per frame by whatever owns the camera, read by the mixer. A torn read costs very slightly wrong panning, which nobody hears. A lock on a real-time thread risks a priority inversion, which everybody does.

Voices, buses and the underrun counter

Voices are a fixed pool, 64 by default. Running out doesn't fail and doesn't allocate — it steals a voice, and a stolenVoices counter records that it happened. Buses sit above the voices, with a master volume over the top.

Underruns are counted too. That counter is the number worth watching: a dropped render frame is a stutter, and a dropped audio buffer is a click, and the two do not deserve the same tolerance.

The seam is 24 exports, which is also the reason docs/ABI.md is out of date — it documents seven seams and 201 exports, and the tree has eight and 225. The word “audio” doesn't appear in it at all.

WASAPI, chosen for testability rather than taste

The device backend is WASAPI in shared mode, and the reason it isn't XAudio2 is stated directly: XAudio2 would own the mixing, the 3D and the DSP, which would make Aver.Audio a wrapper around a thing it can neither test nor port.

That's the same build-versus-vendor call the rest of the engine keeps making — it already hand-writes its own D3D12 backend and its own JSON reader. Owning the mixer is the point, because the mixer is the part with the bugs in it.

The render thread joins Windows' Pro Audio scheduling class via avrt. An ordinary thread preempted for ten milliseconds is a gap somebody hears.

The .ocaudio container

Audio ships in the same AVR1 container as every other native format: the shared 64-byte file header, a chunk directory, 16-byte chunk alignment, a CRC32C over the header and an xxHash64 over each chunk payload. Audio adds two chunks — AHDR for the header and APCM for the samples.

Import is a hand-written WAV reader plus Windows Media Foundation for mp3, m4a, aac, wma and flac. Media Foundation was chosen so those formats don't require vendoring a decoder under the engine's permissive-licence-only rule, and Aver.Formats.Audio is its own target linking mfplat mfreadwrite mfuuid ole32 — so nothing else in the tree pays for that dependency.

One caveat worth stating, because the test suite states it: OcAudioTest passes but skips the Media Foundation check. The WAV path and the container are tested. The mp3, m4a, aac, wma and flac path is exercised by nothing, and that skip is invisible in an exit code.

The module split — why the mixer needs no device to be tested
# Core-only. mix() fills a buffer the caller supplies; opens nothing.
aver_add_module(Aver.Audio         DEPS Aver.Core)

# The only target that knows a sound card exists. Windows-guarded,
# the same way the D3D12 backend is.
aver_add_module(Aver.Audio.Wasapi  DEPS Aver.Core Aver.Audio)

# The seam a game calls. SHARED, and it links the DEVICE rather than
# just the mixer - "play a sound" means nothing until something is
# driving hardware.
add_library(Aver.Audio.Abi SHARED ...)
target_link_libraries(Aver.Audio.Abi PRIVATE Aver.Audio Aver.Audio.Wasapi)

# Media Foundation is isolated here, so no other module pays for it.
target_link_libraries(Aver.Formats.Audio PRIVATE mfplat mfreadwrite mfuuid ole32)
