01

Get the launcher and the tools#

Aver runs on Windows and renders through DirectX 12. Before anything else, check the machine can host it — the engine reports every capability from a real device query, so a card that cannot do something will say so rather than fail obscurely later.

  • Windows 10 or 11, 64-bit — the platform layer is Win32.
  • A DirectX 12 GPU with current drivers. Ray-traced shadows additionally want DXR tier 1.1; without it the renderer falls back to the shadow map.
  • The .NET desktop runtime, if you want C#. It is optional: with no runtime present the editor still starts and the scripting menu items disable themselves with a tooltip naming the reason.

Grab the launcher from the download panel on the home page. It installs the engine and keeps it current, and it is the only piece you fetch by hand.

Building the engine from source instead? You need Visual Studio 18 with the C++ workload, which supplies CMake, Ninja and the Windows SDK. Then ./scripts/build.ps1 and ./scripts/run.ps1.

02

Make a project#

A project lives outside the engine. The engine ships no game content; your project is a sibling folder with its own .ocproject manifest, and that separation is why updating the engine cannot disturb your game.

Create one from the project browser on startup, or from the command line — the flag exists so project creation is scriptable rather than something that only happens when someone remembers to click a modal:

PowerShell
Sandbox.exe --new-project D:\Games MyFirstGame
Sandbox.exe --upgrade-project D:\Games\MyFirstGame\MyFirstGame.ocproject

You get a manifest and a content tree: Maps, Meshes, Materials, Textures, Sounds, Scripts. You also get Content/Scripts/Scripts.csproj written at creation time, already referencing the four assemblies you write against, plus a starter M_Default material.

AssemblyWhat it gives you
Aver.ScriptingAverBehaviour, Log, the renderer bindings
Aver.FrameworkActors, pawns, characters, game modes, Entity — pulls Aver.Scene in behind it
Aver.UIHud, Layer, Colour, Rect
Aver.Materials[AverMaterial], MaterialBuilder

All four are referenced whether or not you use them. An unused reference costs nothing, and the alternative is a compile error naming an assembly you have never heard of, in a file the editor generated.

The manifest names a start map, but no map file is written — a fresh project opens with an empty world and logs that it did.

03

Write your first actor#

A gameplay type is a C# class that derives an Aver base type and carries an [AverClass("Name")] attribute naming it. Put this in Content/Scripts/Rotator.cs:

Content/Scripts/Rotator.cs — C#
using Aver.Framework;
using Aver.Scene;      // Vec3, Rot
using Aver.Scripting;  // Log

namespace MyGame;

[AverClass("BP_Rotator")]
public sealed class Rotator : AverActor
{
    // The class RECIPE - run once per class at load, never per instance.
    public static void Configure(ClassBuilder b)
    {
        b.Mesh("Meshes/cube.ocmesh");   // a built-in primitive; no file needed
        b.Ticks(TickGroup.PrePhysics);  // ask to tick
    }

    private float _angle;

    public override void OnBeginPlay(BeginReason reason) => Log.Info("Rotator started");

    public override void OnTick(float dt)
    {
        _angle += 90f * dt;                              // 90 deg/sec
        Self.SetLocalRotation(new Rot(_angle, 0, 0).ToQuat());
    }
}

Three things in there are worth understanding before you write anything else.

Configure runs once per class, not per instance. It is the recipe: what components every instance gets, and whether the class ticks at all. An actor that does not call b.Ticks(...) never receives OnTick.

Hooks are overrides, never attributes. Misspell OnTick and you get a compile error, rather than a method that silently never runs. That is the whole reason the API is shaped this way.

Log, not Console.WriteLine. The editor is a windowed process; console writes go nowhere. Log.Trace, Info, Warn and Error reach the Output Log, and fall back to the console outside a host.

04

Compile it, then press Play#

The Tools menu has two items that look similar and fail differently, which is exactly why they are two buttons:

  • Tools ▸ Compile Scripts — builds only. The editor keeps running whatever it already loaded, so a broken file gives you an error while the previous build carries on. Diagnostics are clickable and jump to file, line and column in Visual Studio, VS Code or Rider.
  • Tools ▸ Reload Scripts — builds, then unloads and reloads live. Your hooks fire again without restarting the editor.

Press Play and the session forms in a fixed order: the state moves to Playing first, then the GameInstance spawns, then the GameMode, then its PlayerController and Pawn, then the pawn is possessed, and finally OnPostLogin fires. Stop reverses it and sweeps every other actor the session spawned.

Nothing survives a reload. Every object is rebuilt from its field initialisers — a counter at 564 restarts at 1. The single exception is [Editable] fields, which live in native storage and survive both Play/Stop and hot reload.

C# — a field you can edit in the Details panel
[AverClass("BP_Spinner")]
public sealed class Spinner : AverActor
{
    public static void Configure(ClassBuilder b) => b.Ticks(TickGroup.PrePhysics);

    [Editable(Min = 0f, Max = 720f)] public float DegreesPerSecond = 90f;

    public override void OnTick(float dt) { /* ... */ }
}
05

Add something to walk around with#

AverCharacter is a first- or third-person walking pawn with the defaults already dialled in — 350 cm/s move speed, a 180 × 34 cm capsule, 160 cm eye height, a 450 cm camera boom, and a jump that clears about 110 cm.

C# — a playable character
[AverClass("BP_Hero")]
public sealed class Hero : AverCharacter
{
    public static void Configure(ClassBuilder b)
    {
        b.Mesh("Meshes/hero.ocmesh");
        b.Ticks(TickGroup.PrePhysics);        // set intent BEFORE the physics step
    }

    public override void OnTick(float dt)
    {
        DriveWithInput(dt);                   // WASD walks, mouse turns
        if (Input.GetKeyDown(Key.Space)) Jump();
    }
}

A GameMode names the pawn and controller it spawns, by string. Many games never subclass the controller and just name the built-in one:

C# — the rules of a play session
[AverGameMode("BP_GameMode",
    DefaultPawnClass = "BP_Hero",
    PlayerControllerClass = "PlayerController")]
public sealed class MyGameMode : AverGameMode
{
    public override void OnPostLogin(Entity controller) =>
        Log.Info($"{controller.Name} joined");
}

The character's origin is its feet, not the capsule centre — so putting it on the ground means setting z to the ground height. And use Teleport rather than setting the transform: moving the transform alone leaves the physics capsule behind.

06

Give it a surface#

A material is a C# class. The .cs under Content/Materials is the source of truth; the .ocmat that appears in Binaries/Materials is build output that the next compile overwrites.

Content/Materials/Crate.cs — C#
using Aver.Materials;

namespace MyGame.Materials;

[AverMaterial("M_Crate")]
public sealed class Crate : Material
{
    public static void Configure(MaterialBuilder b) => b
        .Comment("Painted wood, scuffed. Roughness stays high - a gloss here reads as plastic.")
        .BaseColor(0.62f, 0.48f, 0.31f)
        .Metallic(0f)
        .Roughness(0.78f)
        .Texture(Slot.BaseColor, "Textures/crate_basecolor.png")
        .Texture(Slot.Normal,    "Textures/crate_normal.png");
}

Configure is static because a material is never instantiated and never ticks — it is a description the compiler runs once, at build time. Bind it from a class recipe with b.Mesh("Meshes/crate.ocmesh", "M_Crate"), or at run time with entity.SetMaterial("M_Crate").

Two things that will save you an afternoon. The name in the attribute is what a mesh references — renaming the C# class does not unbind anything, which is the point. And the engine looks in Binaries first, then Content, so a stale hand-authored file cannot shadow the one you just built.

Editing the generated .ocmat is a mistake with a delay on it: it is a build artefact, and the next compile overwrites it. The Details panel's Save to C# writes back to your .cs for exactly this reason.

07

Draw a HUD#

A HUD is drawn from a tick, in screen pixels, top-left origin, +Y down. Not centimetres and not normalised coordinates — every layout number is a pixel.

C# — a health bar
using Aver.Framework;
using Aver.UI;

[AverClass("BP_PlayerHud")]
public sealed class PlayerHud : AverActor
{
    // PostPhysics: draw what the frame settled on, not what it was asked for.
    public static void Configure(ClassBuilder b) => b.Ticks(TickGroup.PostPhysics);

    static readonly Colour Ink   = Colour.Argb(0xFFE8E4DC);
    static readonly Colour Panel = Colour.Argb(0xB0141820);
    static readonly Colour Hurt  = Colour.Rgb(232, 76, 46);

    [Editable(Min = 0f, Max = 1f)] public float Health = 1f;

    public override void OnTick(float dt)
    {
        Rect vp  = Hud.Viewport;                      // NOT the window
        Rect bar = Rect.Anchored(vp, 0f, 1f, 260f, 18f, offsetX: 24f, offsetY: -24f);

        Hud.PushClip(vp);
        Hud.Box(bar.Inset(-6f), Panel);
        Hud.Bar(bar, Health, Ink, Panel, Colour.Lerp(Hurt, Ink, Health));
        Hud.PopClip();
    }
}

Anchor to Hud.Viewport, never to the window. In the editor the game draws into a dock panel and the two rectangles differ, so a HUD laid out against the window sits partly under the editor's own chrome. In a shipped build they are the same rectangle and nothing changes.

There is no text. Nothing in the engine rasterises a glyph yet, so there is no Hud.Text — a HUD today is rectangles, bars and tinted quads. There is also no widget tree and no input routing into the UI: a HUD is drawn, not clicked.

08

What to know before you go further#

A few rules run through the whole API. Knowing them early saves working them out the hard way.

  • Zero is always invalid. A default Entity is invalid, a lookup that finds nothing returns Entity.None, and IsValid / IsAlive tell you which.
  • Set intent before physics, read results after. The world steps between the PrePhysics and PostPhysics tick groups, at a fixed step regardless of frame rate.
  • Everything is centimetres, +X forward, +Y right, +Z up, left-handed. The physics backend works in metres with a different up-axis; that is translated once, behind the seam, and never reaches you.
  • A throw does not take the process down. An exception out of a hook is caught and logged, and that one actor is disabled for the session. Everything else keeps ticking.

And the honest list of what a script still cannot reach: audio — the mixer, device and container all exist and are tested, but nothing is joined up and no managed binding exists, so you cannot play a sound. Text and widgets in the UI. Timers and coroutines — count down in OnTick. Networking. And import beyond glTF: the Content Browser converts .gltf and .glb, and copies every other file type in unchanged.
