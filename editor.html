One binary, no separate editor process

There is no Aver.Editor target and no editor build flag. The editor is Sandbox.exe. ImGui reaches the executable transitively through Aver.RHI.D3D12, which links it publicly and defines AVER_WITH_IMGUI=1 — every editor source file guards on that macro rather than on a separate target.

ImGuizmo was never vendored. Every gizmo in the tree, in the level viewport and the actor preview alike, is hand-built line and overlay geometry.

Because it is one binary, the same executable a person clicks also runs the automated pixel-probe gates. The project browser is deliberately suppressed whenever --frames is present, a project path is given on the command line, or --headless is passed — a full-screen chooser sitting in front of the probe would fail every gate at once.

The shell: docking, panels and a passthrough viewport

The dockspace holds a menu bar, a main toolbar, the dockspace itself and a status bar. World Outliner and Details stack on the right at roughly 22% width. The 3D viewport occupies the transparent central node, so the already-drawn D3D12 back buffer shows through the hole the panels dock around.

Dock layout deliberately does not persist between runs — the ImGui ini file is disabled by design and the layout is rebuilt from the dock builder every launch, with Window ▸ Reset Layout available on demand.

Camera control is free-fly rather than orbit: right-mouse look with WASD and QE, wheel to dolly, middle-mouse to pan, F to focus the selection. Selection picks against each object's local bounding box transformed by its inverse world matrix. Transform tools live as an overlay bar inside the viewport itself, and the gizmos draw always-on-top: arrows for move, three rings for rotate, axis lines with end boxes for scale, with the hovered axis highlighting amber.

Two menus, because C# and C++ are not the same promise

The Tools menu is split into two labelled groups, a deliberate departure from Unreal and the thing most likely to surprise a new user. Under Project — C#, new scripts and classes write into the project's own Content/Scripts/ and need no rebuild. Under Engine — C++, new modules and classes write into the engine's modules/ tree and require a full engine rebuild, because a project manifest carries no build integration — a game project has nowhere of its own to put C++.

Neither CMakeLists is auto-edited. Wiring a new module into the top-level build, or adding a source file to an existing module's explicit source list, is a deliberate manual step — and both dialogs name the exact line to add.

Below those sit two separate actions, kept separate because they fail differently. Compile Scripts only builds, and the editor keeps running whatever it already loaded; its diagnostics render as clickable rows that jump to file, line and column in a detected IDE — Visual Studio, VS Code or Rider. Reload Scripts builds, then unloads and reloads live, firing the lifecycle hooks with no editor restart.

Save to C#, never to the build artefact

The Details panel exposes the live material — metallic, roughness, normal scale, occlusion, reflectance capped at 0.2 because anything above it is gemstone, grazing reflectance, emissive, UV mapping mode and per-slot texture paths. Every control edits the live material description and marks it dirty, so the viewport updates the same frame and objects sharing a material change together.

Save to C# writes the .cs and never the .ocmat. The .ocmat is a build artefact the next compile regenerates, so writing there would appear to work and then silently vanish. Instead the panel walks the project's material sources, and rewrites only the body of Configure — usings, namespace, other classes, hand-authored comment prose and indentation all survive, and only values that differ from the defaults are written.

A file it cannot parse is declined rather than half-written. Compiling then bakes the result back to .ocmat in the same build step; a bake failure keeps the previous file and logs the error rather than turning a bad Configure into a red build light.

The actor editor, and a gizmo that edits source

A .cs file that declares a mesh, camera or point light in Configure, or carries a generated designer region, opens as its own asset editor tab. Everything else is declined — a plain behaviour script is not an actor, and opening it in a tab that shows nothing would take something away.

The tab lays out in three columns: a components tree, the preview viewport, and details. The preview is its own render feature with its own colour and depth target, its own pipeline state, and its own camera published at constant-buffer slot b4 rather than b0 — b0 is the engine's per-frame block and gets rebound on every pipeline change. Lighting is fixed: one key light, a hemisphere fill, ACES and gamma. The panel says outright that it does not match the level viewport, because two independently exposed viewports would need a scene-pass rewrite.

Only one preview instance exists, shared and re-pointed at whichever tab is active, because the UI's shader-visible descriptor heap holds sixteen entries — a target per tab would exhaust it around the eleventh tab with a black image rather than an assert.

A drag rewrites nine numbers, and nothing else

An actor is a partial class split across a hand-written half and a generated designer half. The editor never writes a byte of the hand-written half; it was later permitted to read Configure, because most actors are a single class-declared mesh with no designer file at all, and refusing to look would leave the tab empty for the common case.

The generated region is bounded by exact marker comments rather than #region — plain comment trivia, a span and nothing else. Every placement is one fixed token sequence carrying an object id, a mesh path, a material, and position, rotation and scale triples.

On save, the rewriter finds the statement whose object id matches the placement you dragged — matched by id, never by file position, so a reordered region still finds the right line — and replaces only the nine numeric literals. Property names, mesh paths, the id suffix, whitespace, comments and statement order survive byte for byte. Numbers are quantised and formatted in invariant culture so an unmoved model re-saves to an identical byte stream.

Live edits, and the one thing it refuses to do

The tab stats the file's modification time once per visible frame rather than watching the filesystem — a directory watcher was tried and rejected on contact, because a build running with its working directory inside the scripts folder overflows a recursive watch on its own churn.

If the file changes on disk and the tab is clean, it silently re-parses and reloads. If the tab is dirty, the reload is refused outright: “The file changed on disk. Save or discard to pick it up.” Silently clobbering an in-progress drag with whatever a background tool just wrote is called out in the design docs as the one behaviour a live-sync feature must never have.

A file with no generated region opens as a pure viewer — there are no placements to drag, nothing can mark the tab dirty, and Save never enables. A file whose region has drifted outside the locked grammar is declined loudly, with the reason logged, rather than opened silently as an empty tab.
