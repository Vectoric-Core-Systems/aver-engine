One binary, no separate editor process

There's no Aver.Editor target and no editor build flag. The editor is Sandbox.exe. The concrete Dear ImGui binding lives in its own module, Aver.RHI.D3D12.ImGui — with a Vulkan counterpart, Aver.RHI.Vulkan.ImGui — which only Sandbox links; Aver.RHI.D3D12 itself never links ImGui or defines AVER_WITH_IMGUI. Sandbox defines AVER_WITH_IMGUI=1 itself, gated on Aver.RHI.D3D12.ImGui existing as a target, so every editor source file still guards on that one macro rather than on a separate target.

ImGuizmo was never vendored. Every gizmo in the tree, in the level viewport and the actor preview alike, is hand-built line and overlay geometry.

Because it's one binary, the same executable a person clicks also runs the automated pixel gates. The project browser gets suppressed whenever --frames is present, a project path is given on the command line, or --headless is passed — a full-screen chooser sitting in front of the probe would fail every gate at once.

The shell: docking, panels, and a viewport you can see through

The dockspace holds a menu bar, a toolbar, the dockspace itself and a status bar, with the World Outliner and Details stacked on the right at roughly 22% width. The 3D viewport takes the transparent central node, so the already-drawn D3D12 back buffer shows through the hole the panels dock around.

Dock layout deliberately doesn't persist between runs. The ImGui ini file is disabled by design and the layout is rebuilt from the dock builder every launch, with Window ▸ Reset Layout there if you drag something somewhere regrettable.

The camera is free-fly rather than orbit: right-mouse look with WASD and QE, wheel to dolly, middle-mouse to pan, F to focus the selection. Selection picks against each object's local bounding box transformed by its inverse world matrix. The transform tools live in an overlay bar inside the viewport, and the gizmos draw always-on-top — arrows for move, three rings for rotate, axis lines with end boxes for scale, hovered axis in amber.

Two menus, because C# and C++ aren't the same promise

The Tools menu splits into two labelled groups. It's a deliberate departure from Unreal and probably the thing most likely to surprise someone arriving from there. Under Project — C#, new scripts and classes write into the project's own Content/Scripts/ and need no rebuild. Under Engine — C++, new modules and classes write into the engine's modules/ tree and require a full engine rebuild, because a project manifest carries no build integration — a game project has nowhere of its own to put C++.

Neither CMakeLists gets auto-edited. Wiring a new module into the top-level build, or adding a source file to an existing module's explicit source list, stays a manual step, and both dialogs name the exact line to add.

Below those sit two separate actions, kept separate because they fail differently. Compile Scripts only builds, and the editor keeps running whatever it already loaded; its diagnostics render as clickable rows that jump to file, line and column in a detected IDE — Visual Studio via vswhere, VS Code or Rider. Reload Scripts builds, then unloads and reloads live, firing the lifecycle hooks without an editor restart.

Save to C#, never to the build artefact

The Details panel exposes the live material: metallic, roughness, normal scale, occlusion, reflectance capped at 0.2 because anything above that is gemstone, grazing reflectance, emissive, UV mapping mode and per-slot texture paths. Every control edits the live material description and marks it dirty, so the viewport updates the same frame and objects sharing a material change together.

Save to C# writes the .cs and never the .ocmat. The .ocmat is a build artefact the next compile regenerates, so writing there would look like it worked and then quietly vanish. Instead the panel walks the project's material sources and rewrites only the body of Configure. Usings, namespace, other classes, hand-authored comment prose and indentation all survive, and only values that differ from the defaults get written.

A file it can't parse is declined rather than half-written. Compiling then bakes the result back to .ocmat in the same step, and a bake failure keeps the previous file and logs the error rather than turning a bad Configure into a red build light.

The actor editor, and a gizmo that edits source

A .cs file that declares a mesh, camera or point light in Configure, or carries a generated designer region, opens as its own asset editor tab. Everything else is declined. A plain behaviour script isn't an actor, and opening it in a tab that shows nothing would be taking something away.

The tab lays out in three columns — components tree, preview viewport, details — collapsing to two when it gets narrow. The preview is its own render feature with its own colour and depth target, its own pipeline state, and its own camera published at constant-buffer slot b4 rather than b0, since b0 is the engine's per-frame block and gets rebound on every pipeline change. Lighting is fixed: one key light, a hemisphere fill, ACES and gamma. The panel says outright that it doesn't match the level viewport — no bloom, no eye adaptation, no GI, no cascades, no MSAA — because two independently exposed viewports would need a scene-pass rewrite.

There's only one preview instance, shared and re-pointed at whichever tab is active. The UI's shader-visible descriptor heap holds sixteen entries, and a target per tab would exhaust it around the eleventh tab — with a black image rather than an assert, which is worse.

The node canvas, and the panel that makes it usable

The editor opens .ocgraph files on a node canvas: a palette, wired pins, and the same file on disk that the runtime compiles. The text is the format and the canvas is one way to produce it, so a graph stays diffable and hand-editable either way. See Aver Node for what the graphs themselves are.

It can open real graphs now, which it could not before 0.3. ENTRY and OUT records may name a node declared further down the file — the style every graph here is written in. The C++ reader validated that inline while the C# one deferred it, so the editor refused the sample projects, the demo, and every template graph while the runtime ran them all quite happily.

Saving keeps every record where its author put it. Records are matched individually rather than a whole kind being re-emitted at that kind’s first line — which used to haul every NODE up to the first one and separate it from the comment explaining it. Line endings survive too.

A Variables panel declares, renames, retypes and deletes. Validation rejects a graph addressing an undeclared variable, and until this release nothing in the editor could declare one, so dragging SetVar off the palette produced a graph that could not compile and could not be fixed from inside the editor. Renaming offers to rewrite every node addressing the old name rather than orphaning them.

Panning is right-drag, alongside the existing Space-drag and middle-drag, with click and drag separated by a movement threshold so a right-click still opens Add Node.

A DOMAIN material graph opens on the same canvas, but its Viewport tab shows a sphere instead of the usual component preview — shaded by the graph itself, compiled through the same registry the renderer uses. It has no components to preview: no CLASS record, no actor. The add-node palette also changes shape with it, offering only the open graph’s own vocabulary, so a material graph is never offered a gameplay node whose only possible outcome is a compile error. See Materials, wired instead of written.

A drag rewrites nine numbers, and nothing else

An actor is a partial class split across a hand-written half and a generated designer half. The editor never writes a byte of the hand-written half. It was later allowed to read Configure, because most actors are a single class-declared mesh with no designer file at all, and refusing to look would have left the tab empty for the common case.

The generated region is bounded by exact marker comments rather than #region — plain comment trivia, a span and nothing else. Every placement is one fixed token sequence carrying an object id, a mesh path, a material, and position, rotation and scale triples.

On save, the rewriter finds the statement whose object id matches the placement you dragged — matched by id, never by file position, so a reordered region still finds the right line — and replaces only the nine numeric literals. Property names, mesh paths, the id suffix, whitespace, comments and statement order survive byte for byte. Numbers are quantised and formatted in invariant culture, so a model you didn't move re-saves to an identical byte stream.

Live edits, and the one thing it refuses to do

The tab checks the file's modification time once per visible frame rather than watching the filesystem. A directory watcher was tried and rejected on contact: a build running with its working directory inside the scripts folder overflows a recursive watch on its own obj/ churn.

If the file changes on disk and the tab is clean, it re-parses and reloads silently. If the tab is dirty, the reload is refused outright — “The file changed on disk. Save or discard to pick it up.” Quietly clobbering an in-progress drag with whatever a background tool just wrote is named in the design docs as the one behaviour a live-sync feature must never have.

A file with no generated region opens as a pure viewer: nothing to drag, nothing that can mark the tab dirty, Save never enables. A file whose region has drifted outside the locked grammar is declined loudly with the reason logged, rather than opened silently as an empty tab.

Four editor modes replace one always-on toolset

EditorMode is a four-value dropdown — Select, Landscape, Foliage, Simulate — with a left-docked Mode panel that only appears outside Select, since Select's own tools already live in the toolbar and a panel there would have repeated them at 20% of the viewport's width for nothing.

Landscape sculpting gets undo for the first time. handleSculpt never called pushEdit, so Ctrl+Z after ten minutes of terrain work undid whatever object had last been moved, not the last stroke. One bounded before/after rect-diff now pushes per stroke, not per frame and not a whole-section snapshot. Brush falloff (BrushParams::falloff, defaulting to 1.0 so the old hardcoded curve is exactly reproduced) and a Generate button exposing terrainHeightAt — previously correct code with no UI in front of it — land alongside it. Foliage painting places real scene entities with the same batch-undo treatment.

Mesh Paint and Modeling are absent from the four-value enum entirely, not offered and disabled. Mesh Paint has no vertex-colour channel to paint into, and Modeling's own editor is a read-only stats table — both would have been a dropdown entry opening an empty panel, and that's worse than not offering it at all.

Weather that finally survives a save

Sun intensity, fog density and Fog Tint were each live in the viewport and gone on reload, and each broke a different way. applyLevelSky mapped a loaded level's sunLux into sunIntensity, but nothing on the save side ever wrote sunLux back, so the file's original brightness came straight through the passthrough regardless of what the slider now said. Fog density was split across two members — one filled on load, a different one read on save — so editing it did nothing in either direction. And Fog Tint specifically was never marked edited on a level whose file carried no prior FOG record, the exact bug an earlier commit had already closed for Sun and Sky and missed here. A new --save-level flag makes the round trip provable outside a person sitting at the window: halving sunIntensity before a save came back 50000 unchanged before the fix, 25000 after. (e22f280)

That fix covered three fields. The Details panel offers about forty controls under Sun, Sky and Fog; the level file format carried five. The sun's colour temperature and disk size, the authored sky dome, six air-scattering parameters, the ground and sky-light colours, four of the five height-fog values, and all seven Volumetric Clouds controls moved the viewport and were gone the moment the editor closed, with nothing said about it. A further ~30 fields now persist, using whichever of two conventions fits the field rather than one rule applied everywhere: the existing negative-sentinel convention stays for the eight air parameters, which are strictly positive and can never collide with it, while everything else — fogHeight, fogStart, cloudWind, cloudsEnabled — uses plain token presence, since zero is an ordinary authored value for all of them and a sentinel rule would make each one unsettable. Clouds gets its own record and its own has-flag, distinct from cloudsEnabled itself, so “this level turned clouds off” and “this level never mentioned clouds” stay distinguishable. The two independent hand-written copies of the sky-to-GPU mapping in SandboxApp and GameApp are now one function, applyLevelEnv, with an exact inverse, captureLevelEnv; a level authored with every new token round-trips through a real editor save unchanged, verified field by field down to a negative wind component. (3e2a38c)

A crash reporter for when the engine can't report anything itself

LogLevel gains Critical, which wakes the reporter, and Fatal, which writes a report and terminates — appended after the existing levels, never inserted between them, since the editor persists its log-filter setting as a bare integer and a value in the middle would silently renumber every stored filter. Critical shows dark red on a tinted row; Fatal is black on red, legible only because of the row tint, since this editor's panels sit at 0.07–0.15 luminance. Both levels are mirrored through the C ABI and the C# logging surface.

AverCrashReporter.exe is a separate process linking nothing from the engine but Win32 and the CRT, because it has to still run when the engine that spawned it cannot. Verified with a new --crash-test, which immediately found a real bug of its own: AVER_DEBUGBREAK with no debugger attached raises EXCEPTION_BREAKPOINT, and the exception filter was misfiling that as a generic crash — discarding the assert's own expression, file and line, the exact information a crash report exists to keep.

A command console in the drawer

A third drawer tab sits beside Content Browser and Output Log, reachable from the View menu, a status-bar button, --drawer console, or a backtick keybind. It keeps its own scrollback rather than the engine's — a command's answer interleaved with whatever the renderer happened to log that frame would be unreadable — plus Up/Down history and Tab completion.

frametime prints the per-pass GPU span tree the D3D12 backend has collected for a while — inclusive and exclusive milliseconds and percent of frame for each pass, alongside the whole-frame CPU figure so a GPU-bound frame reads apart from a CPU-bound one at a glance. Getting a bounded --frames capture to answer this at all needed IDevice::gpuTiming() exposed above the RHI first, since the span tree existed but nothing outside the backend could read it; an unsupported backend says so explicitly rather than printing zeroes a reader could mistake for a measurement. vars, get and set read and write voxi.* and post.* live, routed through the same Renderer::setSettings call the UI uses so a console-issued dial doesn't accidentally skip the tier-derivation logic a raw struct write would.

Building it surfaced an unrelated, purely cosmetic bug in the same area: the viewport's bottom-left hint anchored to a fixed point that never accounted for an open drawer, so it drew straight through the last ~70 pixels of whichever one was open. Harmless over Content Browser or Output Log, where that row is just more content — not harmless over Console, where that row is the input line the tab exists for, and the hint being non-interactive meant it could still be typed into blind underneath it. The hint now rides the drawer's own animated height instead of a fixed offset.

Seven editor controls that lied, and one that could cost you an hour

Closing an unsaved graph or sound-editor tab destroyed it outright, with only a warning written to a drawer the user was probably not watching — an hour of work gone to a click on the wrong tab's close button. It now prompts Save / Discard / Cancel, modelled on the application's own exit prompt down to the button order and the rule that a failed save keeps the dialog open rather than closing it and losing the work anyway.

The Static Meshes and Atmosphere show-flag checkboxes in the View menu shared one stack-local boolean, re-initialised every frame — so both always rendered checked and neither ever toggled anything, despite the backend already gating on real state for both. World Outliner and Details, once docked closed, could never be reopened: both menu items discarded their return value against a window with no way to flip it back on. And Sun and Sky slider edits in the Details panel were silently discarded on save for any level whose file didn't already carry a Sun or Sky record — closed here for those two records; the identical gap in Fog Tint, missed by this same commit, is the one e22f280 closed above.

Smaller in the same pass: the Preferences log-filter combo couldn't express two of its own five levels, so choosing Error+ in the drawer's copy left this one blank; Select None cleared the selection index but left a second, related field pointing at the old object; and Build Geometry — a menu item with no CSG system behind it and no plan for one — is deleted rather than left as a label with nothing behind it.

Project Name, Author and Start Map can be changed from the editor

Project Settings > Description used to be five lines of read-only text. Name, Author and Start Map are editable fields now — saveProjectManifest already wrote the whole manifest through writeOcproject, which already owned all four fields; only the widgets were missing.

Renaming updates the manifest's NAME field only, not the folder or the .ocproject filename, and the control says so on hover rather than in a doc somewhere — the project's name also feeds the C# namespace new scripts and materials are generated into, so a rename leaves existing files in the old namespace and starts new ones in a different one. Engine and Content stay read-only, each with its own on-hover reason: Engine is a minimum requirement rather than a preference, and Content is where every asset path resolves from, so an editable field there would break the very session it was used in.

Preferences that persist no matter which control changed them

Changing fly speed with the mouse wheel, flipping Lit/Wireframe from the viewport toolbar, switching the Content Browser to List view, or dragging the drawer taller all survived until the editor closed and then reverted. flushEditorPrefs() writes the preference store correctly; the only thing that ever pushed live editor state into that store was a call sitting at the tail of the Preferences window's own build function, gated on that window being open. Every one of those four controls has a more convenient path that changes the same member and never went near it. The fix syncs at shutdown instead, reading whatever the live members actually hold rather than caring which UI last touched them — which fixes all four at once instead of one call site at a time.

Nine Post Process controls — Exposure, Auto Exposure, Middle Grey, Adapt Speed, Exposure Min/Max, Bloom, Threshold and Knee — now ride editor.ini the same way, with one deliberate exception: neither the load nor the save runs during a bounded --frames capture. A post chain whose default state changes the rendered image would invalidate every pixel-gate oracle the moment two machines had different stored preferences, and it's measured, not assumed — the gate probe used to verify this reads 98,56,50 with the guard in place and 192,138,127 without it. Beside both: a Clear button and a Reset All for keybind conflicts, whose own conflict message had been telling users to “clear it first” with no Clear control anywhere on the page.

A saved render scale sits in the same preference file and could brick the editor outright — see the Renderer for the render-target mechanics — and the only recovery before that fix shipped was hand-editing editor.ini directly, which is why it's worth a mention here too.

New Project was writing manifests the engine refused to load

writeOcproject emitted the required OCPROJECT header only on its from-scratch code path. Every real project scaffold — New Project, --new-project, and every template — passed a three-line comment preamble instead, which routed through the other branch and wrote no header at all. loadOcproject then rejected the very file the editor had just written, and the guard covering a failed scaffold deleted the half-made folder behind it. New Project simply did not work, in the editor or on the command line, and nothing about the failure pointed at the header.

A project name is allowed to contain spaces and hyphens because it names a folder, not an identifier — but three of the generators pasted that name directly after namespace, so a project called “My Game” emitted invalid C# into its own starter material, actor scripts and behaviours, and the first Compile Scripts would have failed pointing at files nobody had hand-written. Both fixes are covered end-to-end against a real scaffolded project now, not only against the sanitiser in isolation. New Material also reaches the Content Browser's + Add menu for the first time — the generator behind it has existed since materials gained a node compiler, with zero callers until this commit.

Five controls whose code already worked

The .ocmesh viewer's “3D preview” tab had been claiming it needed infrastructure that already existed — the same ActorPreview target, orbit camera and texture handle the Content Browser's own thumbnails render through. It's wired now, and works with no project loaded at all, since it uploads from the already-parsed mesh data directly rather than through the path that resolves against a project's content root.

File > Save Level As lets you name a new level file — the toolbar's own Save tooltip had been telling people to do exactly this for as long as the tooltip existed, with no such control present anywhere in the File menu. Help > About shows a dialog instead of quietly discarding its own return value. Recent Projects gains a way to remove an entry without hand-editing recent.txt — the removal function has been public since the class existed, reachable only from the one code path that runs after a project fails to open. And dragging a Transform field's number in the Details panel is undoable now, matching the gizmo drag it had always been inconsistent with.

Add > Sphere, and two other buttons that stayed enabled and did nothing

sphere.ocmesh has been a registered built-in mesh since startup, alongside the cube — and Add > Sphere was disabled the entire time regardless, because spawning only ever knew how to spawn a cube. spawnCube is spawnPrimitive(asset, label) now, so any registered mesh spawns the same way; existing callers keep working through a thin wrapper.

AnimEditor's “Move to selected bone” stayed enabled with no bone selected and silently did nothing, unlike its own sibling “Add on selected bone” two rows above, which has always been disabled with a stated reason in that case — the two now match. BtEditor's Move Up and Move Down buttons stayed clickable and inert at the ends of a sibling list, the only two controls in that toolbar not gated at all; they're checked by the same predicate the move operation itself calls first now, so the button and the operation can't drift into disagreeing about whether a move is possible.

The start screen's project list and its selection could point at different projects

Recent projects and the cards displaying them were two index-parallel containers with nothing enforcing agreement between them. Open Selected was disabled outright for any folder-scanned project past the end of the recent list — roughly half the visible rows — with no reason given, though double-clicking the same row worked fine. A failed open could leave the selection pointing at a different project than the one just clicked, and rebuilding the list after a version-upgrade could leave a stale integer meaning whichever project now happened to occupy that slot.

Selection is a resolved path now, not an index into whichever container happens to be in scope — which makes the whole class of bug unrepresentable rather than patched at each call site. Fixing it this way also surfaced that three of the browser's four open paths skipped the version-upgrade gate entirely, and that every project following the Game.ocproject naming convention showed up as an identical “Game” row, since the card label was the file stem rather than the manifest's own NAME field.

The Player Start is a viewport marker now, not a white cube

It draws as a camera-facing billboard inside the transparent pass rather than as a screen-space overlay, specifically so it's occluded by walls the way everything else in the scene is — an overlay would show a spawn marker through solid geometry, which is a marker lying about where it is. It's excluded from the opaque pass, the shadow cascade, GI voxelisation and the ray-tracing structure by entity identity, not by clearing its visibility flag, which would also have made it unclickable; its pick volume was widened to cover the whole visible pin rather than a box centred on the entity origin that left the top half unclickable and 50cm of empty floor clickable instead. It hides automatically the moment any kind of Play session starts — a real GameMode, or either of the two built-in stand-ins — combined into one shared check that three separate call sites had each previously spelled out by hand.

File > New Level could leave the previous level's marker behind, rendering in an empty level, and worse, leave Add > Player Start finding that stale marker still valid and selecting it instead of creating a new one — so a fresh level couldn't be given a spawn point at all. The marker is deliberately kept out of the level's own entity list (recording it there would duplicate the spawn point across two record kinds), which is exactly why the ordinary per-entity teardown loop can't reach it; it's released by name in level teardown now, the same fix already made once before for a simulated fluid volume that had the identical shape.

The selection outline, wrong in two different ways

Wireframe selection made the outline shader decline the pipeline and fall through to the engine's ordinary lit shader, complete with fog — so the outline's brightness depended on which way each face of the selected mesh happened to point toward the sun, dark on one side and blown out on the other, when selection orange is supposed to mean “selected” and nothing about the lighting. An existing-but-unused unlit bypass is reached now through IDevice::setUnlit(bool), which turned up a second bug on the way in: the bypass returned the authored colour without the linear-to-sRGB step every other exit of that function applies, so ACES tonemapped it as though it were already linear and selection orange came out visibly yellow (a green/red ratio of 0.92 against a correct 0.80).

Separately, selecting anything under path tracing folded a second, slightly oversized copy of the outline into the accumulated image, because every draw call reaches every registered render feature before the path tracer's own scene-suppression flag is consulted — and the path tracer has no way to tell an editor-only outline draw from ordinary scene geometry once it arrives. A new sceneSuppressed() query lets the outline's own interactive-only gate exclude it from the path tracer specifically, implemented on both backends even though Vulkan ships off by default, since a divergence that only ever shows up as a rendering difference between backends is the hardest kind to find later.

The fly camera could get stuck on with the cursor hidden

The check that turns fly mode off on mouse release lived inside the same conditional block that decides who owns input this frame — fine under the old, broader arbitration rule, but the newer one splits keyboard ownership from mouse ownership and is strictly narrower, leaving states where that block doesn't run at all. Release the right mouse button while a text field is focused and the pointer sits off the viewport, and the camera stays in fly mode with the cursor hidden until something else happens to re-enter the block. Exiting fly mode is unconditional now, the same fix already applied elsewhere this cycle to a state whose only reset lived inside a conditional that could stop running. A related one-frame-stale read — the fly camera consulting who owns input before that answer was resolved for the frame — is fixed alongside it.

Browsing a level was running its gameplay graphs the whole time

Two thirds of a typical Output Log turned out to be one diagnostic line, firing every frame for every ticking entity, with no play session running at all. Measured on a scene with three placed targets and a rules object over 120 frames: 479 of 718 lines were that one line. Fixed to fire once per entity — the log dropped to 242 lines — but the more important half of that discovery was what the noise was hiding: those lines were firing at all with nothing driving them.

A placed graph's own class instance ticked every frame in Select mode, unconditionally, with no begin_play anywhere in the log. Measured over 1000 frames with Play never pressed: a graph's own variable climbed continuously to 12.3 seconds and logged over 4,000 ticks. The comment defending this behaviour argued a graph-only project has no way to gate on play state, since it has no C# GameMode to find — disproved by the project's own log, which shows a graph-declared GameMode registering into the identical native slot a C# one uses. Gameplay ticking is gated on the same play-state check the framework's own tick groups already use; animation, particles and previews are deliberately left ticking unconditionally, since freezing those in Select mode would defeat the point of an editor preview.
