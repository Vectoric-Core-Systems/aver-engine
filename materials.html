Materials, wired instead of written

Two pipelines, not one replacing the other

Aver has had one way to author a surface since before this release: a C# class under Content/Materials, compiled by avermatc into a .ocmat — see Materials authored in C#. 0.4 adds a second, and it does not replace the first: a .ocgraph carrying a DOMAIN material record is the material, wired instead of written, compiled by a different compiler entirely (modules/render.pbr/src/MaterialGraphHlsl.cpp, not avermatc) straight to HLSL rather than to a .ocmat file.

The reason to reach for one over the other is concrete, not stylistic. MaterialBuilder.Configure sets static factors and texture slots — BaseColor, Metallic, Texture(Slot.BaseColor, path) — decided once, at build time. There is no way to ask it for a value that depends on where on the surface a pixel is. A graph can, because its nodes read per-pixel inputs — world position, UV, the view direction, the camera — and compute an expression over them. The worked example below draws bands across a cube for exactly that reason: no C# call in the existing builder API could have produced it, because the builder has nothing that varies across a surface to call.

DOMAIN material, and the third answer

A .ocgraph file can now carry one optional second line, DOMAIN <name>, naming which language its nodes are written in. It is deliberately a three-way answer, not two.

No DOMAIN record at all means gameplay — every graph written before this record existed keeps compiling exactly as it did, because absent cannot be an error. DOMAIN material means the compiler above: nodes that shade a surface, compiled to HLSL. Anything else — DOMAIN sound, DOMAIN vfx, a name this build has never heard of — resolves to Unknown, and every consumer skips it. That is not the same answer as gameplay: a file that explicitly names a domain this build does not recognise is telling it “not mine,” and folding that back into gameplay would mean compiling a graph whose own author said it wasn’t one. The domain name round-trips through a load and save unchanged either way, so an older editor opening a newer project’s DOMAIN vfx graph does not quietly rewrite it into something it does understand.

One more asymmetry worth knowing: DOMAIN with nothing after it is a parse error, not a graph read as domain-less. The two mean opposite things to the code that asks “is this one mine,” so a file that says the word and then says nothing gets a defect report instead of silently becoming a gameplay graph.

GRAPHREF, and a graph that can be partial

A .ocmat binds a material graph with one new record: GRAPHREF <path>, content-relative, the same way a mesh path resolves. What it drives is only the MaterialOutput pins the graph actually wires up — BaseColor, Metallic, Roughness, Normal, Emissive, Occlusion, Opacity, AlphaCutoff. A pin counts as driven when it is linked, or when a literal is typed straight into it — MaterialOutput’s pins carry no default value in the palette for exactly this reason, so a non-empty one is unambiguously something a person wrote. Every field the graph does not drive keeps whatever the .ocmat’s own PARAM block and texture maps already said.

That is what makes a graph partial rather than all-or-nothing: MG_Bands.ocgraph below wires up BaseColor and types a literal into Roughness, and leaves Metallic, Normal, Emissive, Occlusion and Opacity alone entirely — so the material bound to it still has this project’s own metallic factor and normal map, exactly as if the graph had never touched them.

One shader for every material

The obvious design — one compiled shader per material graph — was considered and rejected once it was measured against how this renderer actually works. Every standard material in Aver already shares one pipeline and differs only by a binding set and a small constant block; per-material shaders would have been this engine’s first per-material pipeline variant, a change to the hot draw path and its sorting and lifetime rules, bought to render one cube.

What shipped instead: materialGraphHlsl() emits one generated function, averEvalMaterial, with a case per compiled graph inside a single switch on gMaterialGraphId — a value that is constant across an entire draw, so every GPU lane in that draw takes the same arm and the cost is that arm’s own, not the sum of every material in the project. The id rides in MaterialConstants::graphId, four bytes that were previously padding, inside a block already uploaded per draw — no new cbuffer. The generated function itself is spliced into the shared prelude behind an AVER_MATERIAL_GRAPH define carried by the prelude text rather than a compiler -D flag, so a project with zero compiled graphs gets a prelude that is byte-for-byte what it has always been.

56 nodes, compiled backwards from the sink

The material vocabulary has 56 node types: four constant constructors, six scene inputs (UV, WorldPosition, WorldNormal, ViewDirection, CameraPosition, ObjectPosition), roughly two dozen math operations, six vector operations, vector construction and swizzling, texture-space helpers (TilingOffset, Rotator, Noise, Checker, SampleTexture), Fresnel, a conditional If, and the one sink every graph needs — MaterialOutput. There is no Time and no VertexColor: the shared shader prelude carries no time uniform and the vertex format carries no vertex colour, so both would have been palette entries whose only possible outcome is a compile error.

Emission is pull, not push: it starts at MaterialOutput and walks backward along the links, emitting a node only when something actually reads it. An author’s half-finished experiment left floating on the canvas, unconnected to anything, is not a compile error — it is simply never emitted, which is dead-code elimination as a property of how the walk works rather than a separate pass. The type system is arity, not a type lattice: there is no bool, no int and no texture handle, only float through float4, and the promotion rules for widening a scalar into a wider input live in exactly one place.

Sixteen node names exist in both vocabularies with different pins. The gameplay Add takes two scalars, because the gameplay pin system has no vector types at all; the material Add takes two float3s. The editor resolves a spawned node by (type, domain) rather than by name alone, and its add-node palette offers only the open graph’s own vocabulary — a material graph is never offered Branch or CharacterMove, because wiring either in would be offering a node whose only possible outcome is a compile error naming a node the palette itself suggested.

The editor previews it on a sphere

Opening a DOMAIN material graph shows a sphere in the Viewport tab, shaded by that graph — compiled through the same registry the renderer uses, keyed on the file’s own path. It is not an approximation of what a placed .ocmat will do; it is literally the same generated function, taking the same case arm. A sphere rather than a cube, on purpose: it presents every angle between the surface normal and the view direction at once, so a Fresnel term, a roughness value and a normal map all read on it, where a cube only shows six flat faces.

A material graph gets its own preview viewport rather than the ordinary component one, because it has no components — there is no CLASS record on a material graph, and the component toolbar’s usual warning about nothing spawning them would be actively misleading on a file that was never supposed to have one.

A broken graph doesn’t take the material down

If a graph fails to compile — wrong DOMAIN, two MaterialOutput nodes, none at all, nothing driven, an unresolvable node — resolution returns id 0, which the generated switch treats as “no graph”: the surface falls all the way back to the stock .ocmat path, unchanged, and the reason is logged. An author mid-edit on a half-wired graph keeps seeing their object rendered with its ordinary material, not a black surface, a magenta placeholder or a crash.

Clear coat

Three fields on a material — CoatWeight, CoatRoughness and CoatF0, all clamping to [0,1] — add a second specular lobe over the base BRDF. Author them as PARAM lines in a .ocmat, through Aver.Materials’ C# authoring builder, or as three MaterialOutput pins on a material graph; a coat weight of 0 (the default) costs nothing and changes nothing, in the shader or in what a .ocmat writes to disk. Turning it on for a project needs a reload — Voxi compiles a coat and a no-coat variant of every scene pipeline at startup rather than switching live, and the Rendering > General control says so on the control itself rather than leaving a stale image on screen. For the composition that makes a coat physically plausible — and the two-sided-attenuation guess that measured wrong — see the renderer’s account.

Subsurface scattering

SubsurfaceWeight and SubsurfaceRadius, both [0,1] and both defaulting to 0, are two more PARAM lines, two more builder calls, and two more MaterialOutput pins — fitted into 8 bytes of padding the material block had already set aside, so no existing .ocmat changes size or shape. It is deliberately not a BSSRDF: no light transport across the mesh, no per-texel thickness, and the transmitted light borrows the surface’s own base colour rather than a scatter tint of its own. At the shipped default (weight 0) it is provably inert — a project that never touches these fields renders and gates byte-for-byte as it always has. What the two floats actually drive is described on the renderer page.

Volume absorption

attenuationColor and attenuationDistance — glTF’s KHR_materials_volume naming — say what a material does to light crossing its interior, as distinct from transmission, which says how much gets through the surface at all. Author a colour and the distance at which that colour is the actual transmittance; the shader inverts it into a per-channel exponential internally, so authoring it needs no notion of an extinction coefficient. No material flag bit was spent adding it: attenuationDistance <= 0 is the off state, so every material authored before this field existed keeps rendering exactly as it did. Water (see Fluids) is simply a material that sets both fields; the path length that turns them into a transmittance is measured by a real traced ray, and the entry/exit and front-face bugs that had to be fixed to make that reliable are on the renderer page, not here.

Refraction

Refraction is a rendering setting rather than a per-material field — Off, ScreenSpace or RayTraced, tier-derived by default (Low/Medium get ScreenSpace, High/Epic get RayTraced), with refractionStrength and refractionEdgeFade left as explicit knobs and a --refraction override for pinning a specific mode regardless of tier. A material only needs an authored ior for the bend to have something to compute from; gIor, present in the material block since before this release, gets its first actual reader here. What ScreenSpace and RayTraced do differently, and the NDC and sign-blindness bugs that shipped before either mode was trustworthy, are covered on the renderer page.

A ray-driven fix: materials read correctly again

Under the ray-driven render mode — the shipped default since 0.4.0 — every ray hit was indexing a default-constructed material for anything beyond albedo, metallic and roughness, because the per-instance material index was uploaded to the GPU before the pass that fills it in had run. An authored coat, a subsurface pair, an ior, a transmission value or a material-graph id could be set correctly on the .ocmat and still render as if none of it existed, because the fallback row a hit landed on instead carried none of it. It hid for exactly the reason it is easy to miss: albedo, metallic and roughness arrive per-draw by a different path and looked right regardless. The engine’s own default probe moved from a fully-metallic, fully-rough (60,32,24) to the correct (70,39,32) once the ordering was fixed — a correction, not a regression. Full detail, including how the bug was isolated, is on the renderer page.

Save to C# stopped destroying an authored glass material

ior and transmission have had a parser, a writer, a GPU packing and a shader consumer for a long time; what they lacked was a way for a script to read or write either, and a place in the editor’s C#-regeneration chain that carried them forward. The editor rewrites a material’s .ocmat from the same C# chain the authoring builder uses on Save to C#, and that chain omitted both fields — so a glass authored at transmission 0.92 and ior 1.52 rendered correctly right up until Save to C# was pressed, after which it came back opaque at the default ior with nothing in the UI to say anything had changed. Both fields now round-trip, and both gain C ABI accessors and C# properties, matching the reach subsurface’s fields already had. Neither field has an editor inspector control or an Aver Node pin yet — stated rather than left for the next person to discover, since routing either through a graph needs the same authored-surface plumbing subsurface and coat both needed first.

MG_Bands.ocgraph — the real graph from test-content/MaterialGraph
OCGRAPH 1
DOMAIN material
# A material graph, and deliberately one that says something no PARAM block can.
#
# frac(worldPosition * 0.02) is a value that CHANGES ACROSS THE SURFACE -- bands every 50 cm in each
# axis, so a 120 cm cube shows more than two of them. A flat colour would prove nothing here: a flat
# colour is exactly what `PARAM baseColorFactor` already does on its own.
#
# ROUGHNESS IS A TYPED LITERAL, not a wire -- a MaterialOutput input counts as driven when it is
# LINKED or when a value is typed into it. Metallic, Normal, Emissive, Occlusion and Opacity are left
# alone entirely, so they keep what this material's own .ocmat declares.
NAME MG_Bands

NODE wp WorldPosition -760 -60
PIN wp xyz out float3

NODE rate ConstFloat3 -760 160
PIN rate value out float3 0.02,0.02,0.02

NODE scaled Multiply -420 30
PIN scaled a in float3
PIN scaled b in float3
PIN scaled result out float3

NODE bands Frac -140 30
PIN bands x in float3
PIN bands result out float3

NODE out MaterialOutput 160 -40
PIN out BaseColor in float3
PIN out Roughness in float 0.25

LINK wp.xyz scaled.a
LINK rate.value scaled.b
LINK scaled.result bands.x
LINK bands.result out.BaseColor
