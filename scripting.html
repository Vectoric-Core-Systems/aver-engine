The CLR lives inside the engine process

Aver hosts the .NET runtime in-process rather than shelling out to a separate managed program. The native side, Aver.Scripting.Host, links Aver.Core and Aver.Platform and never the RHI, and drives the CoreCLR hosting sequence through nethost and hostfxr.

Neither library is linked at build time. Both get LoadLibraryW'd at run time, because a missing import in the executable's own table would kill the process at load on a machine without .NET — which is precisely the case the host exists to handle gracefully. Even the hostfxr declarations are written out by hand rather than included from the SDK headers, since those headers only exist where the SDK does.

Running in the editor's address space is what makes the bindings useful rather than decorative. A P/Invoke from script code resolves to the same native DLL the editor already loaded: the same settings singleton, the same real device capabilities. A separate process gets its own copy with empty caps and can't touch the running editor at all. The proof is in the log — a script that sets global illumination to High produces raw(104,91,104), which is the engine's own --gi oracle value, bit for bit, on a run that passed no --gi.

Lifecycle hooks are overrides, never attributes

There are two authoring surfaces. AverBehaviour is the lower-level base class, with OnStart(), OnUpdate(float dt) and OnShutdown(). Above it is the gameplay object model in Aver.Framework: AverActor → AverPawn → AverCharacter, alongside player controllers, game modes and game instances.

Both follow one rule, stated in both docs: hooks are virtual overrides, never attribute-matched methods. Misspell OnTick and you get a compile error rather than a method that quietly never runs — which is the worst failure mode there is for an audience that isn't made of engine developers. The price is C#'s single inheritance, and that's fine, because an actor is meant to be a leaf type.

A class gets its name from [AverClass("Name")]. The host reflects every AverActor-derived type at load and calls its static void Configure(ClassBuilder b) once per class — not once per instance — to register mesh, camera and light defaults and tick registration.

Hot reload, and the state that doesn't survive it

User assemblies load into a collectible AssemblyLoadContext, fed from an in-memory stream so the DLL on disk is never locked. This is the one decision that couldn't be deferred: an assembly loaded into a non-collectible context can never be unloaded, so it had to be right at first load rather than retrofitted later.

Tools ▸ Reload Scripts rebuilds, unloads the old context, then reloads and re-instantiates. The build runs on a background thread and the swap runs on the main one, because the lifecycle hooks are tied to the frame loop; the build thread only sets a flag. A failed build never unloads anything — break a source file and you get a build error while the previously loaded behaviour carries on running. Unloading is asynchronous, since a collectible context is only collected once nothing references it and a GC runs, so the collect loop is bounded at two cycles rather than spinning forever on a leaked reference.

Nothing carries across a reload. Every object is constructed fresh from its field initialisers. The transcript in the docs is blunt about it: version A shuts down after 564 updates, and version B's counter starts from 1. The one exception is [Editable] fields, which live in native storage and survive both Play/Stop and hot reload.

Two contracts, checked separately

The same C# surface talks to two different boundaries, so there are two version checks. Between the native host and the managed bridge sits AVER_SCRIPTING_CONTRACT_VERSION, plus a struct sizeof check. It's at v3: v2 added hot reload and the UnloadScripts entry point, v3 added the HUD entry points.

Between the bridge and your assembly sits the assembly version of Aver.Scripting — read out of the user assembly's own reference table rather than from an attribute you'd have to remember to write. A mismatch is rejected outright, naming both versions. An assembly that doesn't reference Aver.Scripting at all is skipped in silence, which deliberately lets a Scripts folder hold plain support libraries.

One throwing actor, not one dead process

An exception escaping an [UnmanagedCallersOnly] method doesn't become a catchable C++ exception. It terminates the process. So every bridge entry point is wrapped — and, more importantly, each individual hook call inside a loop over multiple actors is wrapped individually, so one throwing actor doesn't stop the others in the same frame.

An object that throws gets logged and disabled for the rest of the session while its siblings keep ticking. There's no API to list or re-enable it short of a reload.

The host also declines cleanly when scripting simply isn't available — no .NET runtime, hostfxr failing to initialise, or the module compiled out. A missing runtime is never a startup failure: the editor runs normally and the Tools items disable themselves with a tooltip naming the specific reason. Five separate decline branches were tested one at a time, and each produces its own log line.

Materials are C# source, compiled to storage

A .cs file under Content/Materials is the source of truth. The .ocmat under Binaries/Materials is build output nobody hand-edits. One assembly compiles from two source roots — Content/Scripts and Content/Materials — and a successful compile runs avermatc automatically.

That tool reflects the built assembly, finds every class carrying [AverMaterial], invokes its Configure once at build time, and writes one .ocmat per material. A material that fails to bake is reported but doesn't fail the build — the C# compiled fine, so a red light would point at the wrong thing. Two classes claiming the same material name are refused outright rather than resolved last-one-wins, since the winner would depend on reflection order.

Lookup goes Binaries first, then Content. That ordering stops a stale hand-authored .ocmat shadowing the freshly built one, and it means a project that never adopted C# materials keeps working exactly as before.

C# — a behaviour and a material
using Aver.Scripting;

public sealed class Spinner : AverBehaviour
{
    private float _t;

    public override void OnStart()  => Log.Info("Spinner up");
    public override void OnUpdate(float dt) { _t += dt; }
    public override void OnShutdown() => Log.Info("Spinner down");
}

// ---------------------------------------------------------------------------

using Aver.Materials;

[AverMaterial("M_Crate")]
public sealed class Crate : Material
{
    public static void Configure(MaterialBuilder b) => b
        .Comment("Painted wood, scuffed. Roughness stays high - a gloss here reads as plastic.")
        .BaseColor(0.62f, 0.48f, 0.31f)
        .Metallic(0f)
        .Roughness(0.78f)
        .Texture(Slot.BaseColor, "Textures/crate_basecolor.png")
        .Texture(Slot.Normal,    "Textures/crate_normal.png");
}
