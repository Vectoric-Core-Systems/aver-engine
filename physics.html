Vendored, and linked private on purpose

The backend is Jolt Physics 5.6.0, MIT-licensed, vendored at modules/physics.jolt/ and linked PRIVATE into the Aver.Physics shared library. That link keyword is the entire design. Nothing above can include a JPH:: header by accident, which keeps swapping the backend a decision local to one module rather than a refactor across the tree.

You get static boxes, triangle meshes and heightfields; dynamic boxes, spheres, capsules and cylinders; convex hulls (which take a flag for whether they're dynamic); and box and sphere sensors for triggers. Capsules already existed, but only the character controller could have one — physics_shapes_abi.h now puts capsule and cylinder on ordinary rigid bodies too. Bodies and characters draw from one shared handle counter starting at 1; joints get a separate counter of their own, so a joint and a body can carry the same number safely, since neither family ever looks in the other's table. Zero is always invalid in either counter, and handles are never reissued, so a stale lookup misses rather than aliasing whatever took the slot.

Jolt works in metres with a different up-axis. Aver is centimetres, +Z up, left-handed. The translation happens once, behind the boundary, and no caller ever sees a metre or a +Y-up vector. Gravity is in cm/s² and defaults to (0, 0, -980).

A fixed step, whatever the frame rate

The simulation runs at a fixed step regardless of what you pass to step. Jolt's determinism guarantee is stated in terms of the same calls in the same order, and a step that follows the frame rate makes the result a function of machine speed. Leftover time is carried forward and a long stall is clamped, so hitting a breakpoint doesn't fire a hundred catch-up steps when you resume.

aver_phys_step returns how many fixed steps actually ran, which is what you want if you're accumulating anything alongside the simulation.

Set the step before any body exists. Changing it mid-session changes the meaning of every tuned velocity in the project. Ticks are grouped PrePhysics, Physics, PostPhysics, and the convention follows from that: set intent — movement, forces — in a PrePhysics tick, and read what the simulation settled on in a PostPhysics one.

Forces, impulses, and a body that can be pushed

Until this release the only way to move a dynamic body was body_set_position or a velocity setter that overwrote whatever was already there — nothing could be added to it. An explosion, a knockback, a bouncy ball, a rolling one gathering speed or a moving platform were all equally unbuildable. The ABI now covers motion-type control (static/kinematic/dynamic, ordered to match JPH::EMotionType so the two enums can't drift apart), a rotation setter, angular velocity read and write, add-velocity, force, force-at-a-point, torque, impulse and angular impulse, friction, restitution, gravity factor, damping, mass, and activate/deactivate.

Units follow from the two the ABI already fixed — kilograms and centimetres — rather than being chosen independently: force is kg·cm/s², impulse is kg·cm/s, torque is kg·cm²/s² (a force times a lever arm, so centimetres twice), angular velocity is rad/s (radians don't scale). Rotational quantities flip sign going into Jolt. The basis map from Aver's (x, y, z) to Jolt's (y, z, −x) has determinant −1 — that determinant is the handedness change. Ordinary vectors — position, velocity, force — transform by the basis matrix; angular ones — angular velocity, torque, angular momentum — transform by the determinant times the basis matrix and pick up the minus sign it carries. The engine's quaternion converter has carried this sign since it was written; toJoltAngular/fromJoltAngular/toJoltTorque now make it explicit so no future call site has to re-derive it.

BodyDynamicsTest's 63 assertions check observed motion against independently derived numbers rather than return codes, since a wrong conversion still returns success: 200 kg·cm/s of impulse on a 2 kg body gives exactly 100 cm/s; the same force gives 100/60 cm/s of velocity change in one step and nothing more in the next, because Jolt clears accumulated force every step; a body made ten times heavier spins ten times slower for the same angular impulse, which only holds if the mass setter rescaled inertia rather than writing inverse mass alone. The sign claim itself was falsified before being trusted, not just asserted: swapping in the unsigned conversion produced a spin toward the wrong axis, caught by the same test. One thing Jolt won't let this ABI do: there's no runtime "allow sleeping" setter, since MotionProperties only exposes a getter for it in this vendored version — left out rather than faked.

Twelve joint types, and the shapes that were not box or sphere

Jolt's twelve constraint classes were compiled into this engine's binary from the start — Constraints/*.obj is in every build — and none of them had an entry point. A door, a lever, a rope, a chain, a crane, a piston, a swinging sign and a ragdoll were all equally impossible without hand-writing the solver. physics_joints_abi.h now exposes all twelve: fixed, point, distance, hinge, slider, cone, swing-twist, six-DOF, gear, rack-and-pinion, pulley and path, plus motors, runtime limits, enable/disable, and a scalar readback for the two types that have one.

Every point and axis is world-space at creation — not a simplification, but Jolt's own default (every settings struct is EConstraintSpace::WorldSpace), and the only frame a caller can supply without first knowing where each body's centre of mass ended up. bodyB == 0 joins to the world, reusing the handle value already reserved as invalid, which is how a door hangs on a wall that isn't simulated. A joint handle is deliberately not a body handle: bodies and characters share one counter, joints get their own, so joint 1 and body 1 both exist safely, since neither family ever looks in the other's table.

The implementation, the test and the new shapes were written concurrently against the header alone, with the test's author deliberately kept from reading the implementation — a test written by reading the implementation agrees with that implementation's bugs. Both compiled on the first try, and JointTest passed 54 of 54 assertions against the header alone on the first run, which is a fact about the header: two independent readings landed on the same behaviour. Almost none of what it checks is a return code — a hinge to the world swings under gravity while its distance from the pivot doesn't change; a distance joint holds 200 cm exactly, so a metre/centimetre slip lands at 2 or 20000; a fixed joint keeps an 80 cm offset while both bodies fall; a velocity motor turns the hinge and reverses with its target.

Capsule and cylinder join box, sphere, hull, mesh and heightfield as rigid shapes — capsule already existed but only the character controller could have one. ShapeTest drops each shape on a floor whose top is exactly z = 0 and measures where its centre comes to rest: a 200 cm capsule settling at 100.00 is the check that distinguishes a capsule built to the right size from one built to twice or half of it. Capsule height is total, matching aver_phys_character_create rather than Jolt's own half-height convention — a real alternative, so it's pinned by a test rather than trusted to a comment.

Stated rather than hidden: five of the twelve types — fixed, point, distance, hinge and slider, the ones a game reaches for first — carry test coverage today. Cone, swing-twist, six-DOF, gear, rack-and-pinion, pulley and path do not yet. Cone and swing-twist also refuse set_limits outright, since their limits are one angle and four angles respectively, neither of which fits a single (min, max) pair; and six-DOF's Z axis is left as Jolt's own unflipped cross(X, Y), which the engine's determinant-−1 basis change turns into the negative of the equivalent engine-space cross — an asymmetric limit on that axis may read inverted, on the least-used joint of the twelve.

The character controller

aver_phys_character_create(radius, height, x, y, z) and its family wrap Jolt's CharacterVirtual, which is swept and resolved each step rather than force-simulated. That's what gives a walking character controlled movement instead of a capsule that skids and bounces off level geometry.

Height is the total capsule height including both caps, so a 180 cm character passes 180. The velocity you set is what the character wants: horizontal comes from input, vertical is left to the simulation unless you override it — which is how a jump gets expressed.

In C# this surfaces as AverCharacter : AverPawn, a first- or third-person walking pawn with sensible defaults already dialled in. Move speed 350 cm/s, mouse look at 0.2 degrees of yaw per pixel, a 180 × 34 cm capsule, 160 cm eye height, a 450 cm camera boom, and a jump speed of 465 cm/s — about 110 cm of height. IsGrounded is true while you're on ground shallow enough to hold, and IsSimulated tells you whether the physics world is backing the character or it's translating directly.

The controller's own settings have grown to match what Jolt actually offers: max slope, the full four-state ground enum in Jolt's own declared order, ground normal/position/body/velocity (so a character standing on a moving platform gets carried by it), mass, push strength, and a crouch that swaps in a shorter shape — including its failure case, which is the useful half: standing up under a low ceiling is refused rather than growing the character into the geometry above it.

Stair step-up and step-down arrived broken in a specific way worth knowing, because the same shape of bug has shipped here before: Jolt takes them as arguments to its per-step update rather than as state stored on the character, so there's no Jolt-side setter to forward to — the ABI could only record the two numbers, and something has to read them back at the moment of the update. As written, nothing did; the values went into a table the step loop never consulted, so the setter stored a number and changed nothing. Wired through on every step now, and checked behaviourally rather than by inspecting the stored value — a stored-value check is exactly what would have passed before the fix too. The same character walks at the same 25 cm kerb twice: with a 40 cm step-up it travels 746 cm, climbing the kerb and continuing; with none, 100 cm, stopped dead against it. Equal distances would have meant the setter's numbers never reached the update at all.

Collision layers and filtered queries

Until this release the module had exactly two object layers — non-moving and moving — with no way to say "the player's own bullets don't hit the player," "enemies don't collide with each other," or "the camera probe ignores foliage." The only way to express an exception was to not create the body. An object layer now encodes userLayer * 2 + moving: Jolt asks a layer two separate questions — which broadphase tree a body lives in, a performance structure it owns, and who it collides with, entirely the game's business — and answering the first with the whole layer had left the second with nothing to say. The low bit still answers the broadphase question exactly as before; a matrix the caller owns now answers the collision question.

User layer 0 is the default, so a body created without asking for a layer still lands on object layer 0 or 1 — the same two numbers as before, with the same broadphase mapping and the same pair rule. Existing content isn't approximately compatible, it's identical, and that's checked as a regression before it's checked as a feature: a crate still lands on a static floor at its own half-height, and a sensor still fires.

Raycasts, sphere overlaps and sphere casts gain filtered _ex variants rather than wider signatures — the un-suffixed functions are already bound in C#, reached from graph nodes and called across the editor, and widening them would have made every one of those call sites pass a constant they don't need. An ignoreBody parameter earns its place on its own: a ray fired from inside your own capsule hits yourself at distance zero, which is the first bug every first-person weapon has to solve.

Physics as level components

Physics was reachable only from code — a crate could be made to fall by a script at run time and by nothing else, because there was no rigid-body component at all. CRigidBody and CJoint are now registered the same declarative way every other builtin component is, which means serialization and the Details panel inspector both come free: the .ocmap writer is driven by field reflection, and the editor's inspector walks the same field list, so neither needed a line of component-specific code.

CRigidBody carries a shape kind and its dimensions, motion type, mass, friction, restitution, gravity factor, damping, collision layer and a sensor flag. CJoint carries a type, the other entity (zero means the world, matching the ABI's own world-body sentinel), a local-space anchor, two axes, limits and a motor. Both handle fields are read-only in the editor for the same reason a soft body's already is: a physics handle is only valid for the process that created it and must never reach a saved level. Friction and gravity factor get named default helpers because attaching a component through addComponent zero-fills it rather than running its in-class initialisers, and 0.0 is a friction and a gravity factor that neither one wants.

PhysicsSceneSync walks the level and turns these components into real Jolt bodies and joints — bodies first, since a joint names two entities and needs both handles already resolved — and does it on Play, not on load. Building bodies at load would mean a crate settling, drifting and going to sleep while someone was only looking around the level; running it from Play instead means it happens right after the transform snapshot that Stop restores from, and teardown on Stop runs before anything else, because the handles it needs to release live inside components an entity might otherwise take with it into deletion first.

A real play session against a real project found a bug none of the 95 headless suites could: EntryPointNotFoundException: aver_phys_ready, because the new managed assembly and the native module it binds are both named Aver.Physics, and .NET's DLL probing found the managed one first, sitting beside the caller. Fixed with a DllImportResolver, the same way Aver.Scene and Aver.Framework already had to be. Stated rather than hidden: no level in the repository yet places either component, so there's no save/round-trip test for them yet.

Events are polled, never called back

Jolt invokes its contact listener from several worker threads during the step, in an order it documents as non-deterministic. Calling managed code from there would mean marshalling into the CLR from threads it has never seen, mid-simulation, with gameplay then free to mutate the world being stepped.

So contacts and overlaps get buffered into two vectors behind a single mutex, cleared at the start of each step and drained afterwards. What you drain describes the step that just ran, on the main thread, in a fixed order. Those queues are the one piece of genuinely cross-thread state in any of the engine's eight seams, and that mutex is doing real work — worth knowing before anyone concludes the locks are dead weight.

Broadphase queries — raycast, sphere overlap, sphere cast — are documented as non-deterministic in which of several equidistant bodies comes back. Assert that a hit exists and where it is; don't assert which body won a tie.

What the C# side can and can't reach

Corrected from 0.4.0, when only 29 of the entry points (then 36 total) had a binding: all 125 are bound in C# now. A new leaf assembly, Aver.Physics (scripting/csharp/Aver.Physics/), holds the raw P/Invoke surface — Native.cs — plus Body, Joint, Shapes, CharacterBody and real enums for the headers' `#define` groups. It's a leaf like Aver.Scene: it references nothing, and Aver.Framework references it.

Aver.Framework/Physics.cs is a shim now rather than a second P/Invoke surface. Every public member a game script already used — Physics, Body, RaycastHit, ContactEvent, OverlapEvent — keeps its exact shape and forwards, converting Vec3/Quat at the boundary; nothing public was dropped, so no existing script needed to change. This release's new surface — joints, the extra rigid-body shapes, collision layers, the rest of the character controller — isn't re-wrapped a second time under Aver.Framework; a script reaches it with using Aver.Physics; directly, on Joint/Shapes/Physics/Body/CharacterBody.

AbiEnumTest compares every C export against its C# import by name, return type, parameter types and parameter names — the one thing standing between this seam and a silent mismatch. Run across all five headers it found zero binding errors, and four bugs in itself: a line comment containing /* inside physics_joints_abi.h's own header comment ate the rest of the file under a two-pass comment stripper, so the joints and shapes headers parsed to zero exports and surfaced as 29 believable "C# imports a function the header doesn't export" failures instead of the parse error it actually was; a fixed-size array parameter (const float pointCm[3], how nearly every joint spells an anchor) got bracket-stripped down to a scalar for C#, so C read a pointer where C# read a by-value float; a C++ default argument on aver_phys_softbody_create parsed its type and its name incorrectly; and float[]? and float[] — the same pointer to the CLR — compared as different types. The bindings were right throughout; every failure was in the test written to catch them wrong.

The seam now spans five headers — physics_abi.h, physics_character_abi.h, physics_joints_abi.h, physics_layers_abi.h, physics_shapes_abi.h — still POD types only, and still carries no ABI version macro or version entry point: unlike the scene and framework seams, it can't self-report staleness to a caller.

Three bugs a Debug build found, and Release had been hiding

Every physics suite had, until now, only ever run in Release, which compiles out Jolt's own assertions. Run in Debug, three of them died, and none of the three was a Debug-only complaint: a static body's motion properties were read through a call that asserts it isn't static (it "worked" in Release only because the null the assert guards against really is null there); a compound shape was built from box settings that lived on the stack and were destroyed before the compound stopped referencing them, aliasing one dangling address so a three-box table rendered as three copies of the last box — and the existing test had been asserting the resulting wrong resting height, 60 cm, rather than the correct slab-weighted 94 cm; and a hinge or slider built with equal min and max limits, which Jolt explicitly refuses, was silently accepted rather than rejected. All three are fixed, and falsified by reverting each one in turn — with the old code restored, the new checks fail; with the fix back, they pass. 95 of 95 suites now pass in both Release and Debug, which is the first time both configurations have been run at all.

C# — a character driven by input, ticking before physics
[AverClass("BP_Hero")]
public sealed class Hero : AverCharacter
{
    public static void Configure(ClassBuilder b)
    {
        b.Mesh("Meshes/hero.ocmesh");
        b.Ticks(TickGroup.PrePhysics);        // set intent before the step
    }

    public override void OnTick(float dt)
    {
        DriveWithInput(dt);                   // WASD walks, mouse turns
        if (Input.GetKeyDown(Key.V))
            CameraViewMode = CameraViewMode == CameraView.ThirdPerson
                ? CameraView.FirstPerson : CameraView.ThirdPerson;
    }
}
