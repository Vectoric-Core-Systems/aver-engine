Synapse

Synapse advises. It never moves the entity.

A baked 2.5D grid stands in for a navmesh, a dot-product cone plus one occlusion ray is the whole of perception, and a native .ocbt behaviour tree ticks against a registry a project can extend with its own Conditions and Actions. All three are real and tested against no world at all where that is possible — and all three stop well short of what a shipped game's AI needs. This page leads with where.

Three tiers, and one has no scene::World at all

Synapse ships as three separate CMake targets, and the split matters more than any single feature on this page. Aver.Synapse is STATIC and pure — no scene, no physics, no device — and links only Aver.Core and Aver.Formats. It owns the grid, the A* search, and the behaviour-tree evaluator. Aver.Synapse.Scene is where a real scene::World appears at all: components, per-frame ticks, and perception's occlusion raycasts, and it optionally links Aver.Physics directly for that last part. A composition root — the sandbox editor or the packaged game — links both and decides who the AI's one target is and where its events go.

This is not an aspiration; it is checkable in the build files. tests/synapse/src/NavTest.cpp and BtTest.cpp link Aver.Synapse, Aver.Formats, Aver.Core and Aver.Platform and nothing else — no Aver.Scene anywhere in either target's CMakeLists.txt entry. The whole pathfinder is proven against a grid drawn in ASCII, and the whole tree evaluator against a hand-built tree with two fake Condition/Action functions, on a machine with no GPU and no physics at all. It is the identical split Aver.Anim / Aver.Anim.Scene already uses, for the identical reason.

An agent is a target, a status, and a side table

Synapse advises; it never moves anything. That is not a limitation that was discovered — it is the shape the whole system was built around, because a native system structurally cannot do otherwise: AverCharacter's capsule handle is a private C# field with no accessor, and there is no character-movement entry point on the C ABI at all. AgentSystem::tick therefore never calls setLocalPosition and never touches a transform. What it does, once a tick, is advance a baked path and write the agent's current waypoint onto its own component.

CSynapseAgent is nine floats and a status: physical size (radiusCm/heightCm, defaulting to 34/180 to match AverCharacter's own), tuning (moveSpeedCm, turnRateDegPerSec, arriveRadiusCm), a goal, an AgentStatus, and the current steering target. The path itself — the full waypoint list — is not on the component at all. It lives in AgentSystem's own side table, keyed by the entity's full handle and pruned every tick, because the scene's reflection API has no field kind for a variable-length array, and a stale index-only key would hand a recycled entity a stranger's half-finished path. Attach the component with AgentSystem::attach(), never a bare world.addComponent: ComponentPool::add zero-fills its byte buffer and runs no constructor, so an agent attached the raw way gets moveSpeedCm == 0 and simply never moves.

Turning “where should I be heading” into an actual capsule velocity is wired explicitly as three graph nodes, because a graph is the only place code that can move a character lives. SynapseSteer takes an explicit target rather than reading CSynapseAgent itself, on purpose: the identical node does direct chase (target = a seen enemy's live position, from GetSynapsePerception) as readily as path-following (target = GetSynapseTarget's own output), and it never needs to know which. Its real C# implementation clamps forward to cos(yawDiff) floored at 0, leaves right at a hard 0 — v1 steers by turning, never by strafing — and clamps yawDelta to ±turnRateDegPerSec × dt. An agent starting 180° off its target turns in place rather than visibly walking backward first, because forward collapses toward zero as the misalignment grows.

There is no local avoidance. Two agents that both want the same doorway resolve through ordinary Jolt capsule collision, with visible jitter — nothing in Synapse looks for a second agent at all. And one that cannot reach its goal gives up after exactly one query: Unreachable, OffMesh and Invalid all set status Failed once, and the tick never retries it on its own — only a fresh setGoal() call, even with the identical goal, earns another attempt. That is the difference between an impossible goal costing one search and costing one search every frame forever.

Navigation is a baked grid, not a navmesh

Lead with the shape of the limit: this is 2.5D, one floor height per cell. A bridge over a path, or a second storey, is not representable at all. .ocnav is a uniform grid, one OcNavCell per cellSizeCm square (50 cm by default) of the XY plane, carrying only the floor height under it, whether an agent fits, and which connected region it belongs to. The format reserves an NLNK off-mesh-link chunk for the day a bridge needs representing; nothing writes it yet.

A polygonal navmesh was not tried and abandoned — this engine has no voxelisation, contour-tracing or triangulation code anywhere in it, so a real navmesh would be a project of its own. A grid is cheap to bake, cheap to search, and its weakness, coarseness around tight geometry, shows up as a visibly blocky overlay rather than a subtly wrong answer. Baking is an editor command (Build ▸ Bake Navigation, or --bake-nav), never a runtime cost, and not only for performance: terrain collision only exists in the editor, so the bake has to run in the one process where the ground it samples is actually there. It casts one downward raycast per cell for the floor and one upward sphere cast for headroom against the live Jolt scene — and the underlying raycast resolves a hit by a linear scan over every body in the world, so a bake is O(cells × bodies), paid once and shipped as an asset.

Two accuracy limits are worth knowing before trusting a baked grid, and one of them is not really about baking at all. Every level collider — not just for navigation, for every placement in the level — is an axis-aligned box built from a placement's position and scale alone: LevelInstance.cpp calls the physics box constructor with x, y, z, sx, sy, sz and nothing else, no rotation parameter anywhere in the call. A wall rotated 45° collides, everywhere, always, as its own unrotated bounding box, and the bake inherits that same blind spot rather than introducing a new one. Separately, every tree the foliage scattering tool places is written with an explicit nocollide token — a per-tree collider would be an axis-aligned box the size of the whole canopy, blocking a player metres from a trunk they can plainly see they are not touching — so scattered trees have no body at all and are invisible to the bake. Agents will walk straight through them.

The search itself, 8-connected A* with an octile heuristic, returns a status rather than a bool, and the O(1) Unreachable refusal is why every walkable cell carries a 16-bit region id rather than an 8-bit one: 255 distinct regions is reachable in a level with a lot of separated interiors, and a wrapped id would silently alias two unconnected areas together and defeat the exact precheck it exists to run. Returned paths are also string-pulled — consecutive cells in a straight clear line collapse into one segment, so a walk across open ground comes back as two points rather than forty.

Perception: a cone, then one ray

There is nothing here but sight. Hearing and smell were never started — there is no noise-emission call anywhere in the module, and no built-in Condition or Action reads anything but the eyes. CSynapsePerception carries a sight range (3,000 cm), a cone half-angle (45°), a think interval (0.2 s) and an eye height, plus the last target it confirmed and how long ago that was.

The check is cheap first, expensive second: a dot-product test against the observer's forward axis, and only if that passes, one occlusion raycast from eye to target. It is throttled per agent by its own accumulator, not reset to zero but decremented by the interval each time it fires, so a frame that runs long does not push every subsequent check later — perception is a five-times-a-second cost, not a per-frame one. The ray stops 10 cm short of the target's own body, or it would report a hit against the very thing it is checking for and call success “blocked”; it gates on the raycast's return value, never on which entity it reports, because an occluding landscape body is ownerless and reports entity 0 exactly the way a clean miss does.

There is exactly one target, for the whole system, resolved once per tick. Synapse must not link Aver.Framework — it would break the pure/scene split above — so it cannot ask who the player is on its own. It takes a host-installed function pointer instead, called once per PerceptionSystem::tick rather than once per perceiving agent, and every composition root installs the identical one-liner: the controlled pawn of player controller 0. Multiple factions, or a target that differs agent to agent, needs a real code change here, not a parameter.

Eight node kinds, no blackboard, no interrupts

Two things a shipped game's AI usually leans on are missing outright. There is no blackboard: a Condition or Action's parameters are baked into the tree at authoring time, and the only runtime state a leaf can read is whatever fixed component field its C++ implementation was written to read — CSynapsePerception.canSeeTarget, say — not a general key-value store a graph could add entries to. And there is no interrupt: a Selector or Sequence that is Running resumes at the exact child it left off on and never re-checks the siblings before it, so a higher-priority branch cannot cancel a lower-priority action already in progress. Both are real, common behaviour-tree features, and both would be additions to this evaluator, not settings on it.

What is here is a native asset with its own editor tab, deliberately not an Aver Node graph — a graph compiler has no way to model a node whose Running state must survive between ticks, which is the entire reason a behaviour tree exists as a second graph-shaped format at all. Eight node kinds cover it: three composites (Selector, Sequence, Parallel), three single-child decorators (Inverter, Succeeder, Cooldown), and two named leaves (Condition, Action) resolved through a registry a project can add its own entries to. A composite resumes at the same child it was Running on, rather than restarting its subtree — the entire reason a side table of running state exists at all, keyed by the full entity handle and pruned every tick for the same recycled-index reason CSynapseAgent's own path table is.

What .ocbt looks like on disk

It is an AVR1 container: node records with a kind, a parent index, and generic parameters, and nothing more structural than that — children are found by scanning for whichever nodes name a given index as their own parent, exactly the way .ocskel's bones already do, rather than storing an explicit child list anywhere. Parents always precede their children in file order, and node 0 is always the root: there is no separate root-index field to keep in agreement with the array, because a behaviour tree, unlike a skeleton, has exactly one entry point by definition.

No .ocbt ships as a checked-in asset in this tree yet. Every tree that exists on a run of this engine today is written by a test, to a temporary directory, and deleted along with it — there is no authored example to point a reader at. What follows instead is the real record layout from the reader/writer, and the real fixture topology from the editor's own test, quoted rather than invented.

Seven built-ins, and a registry a project extends

Leaves resolve through a name lookup a project can add to without an engine change — an unregistered name is a warning and a Failure, never a crash, matching how an unknown component name is handled elsewhere in the engine. Seven built-ins ship for free, installed by one function call after both AgentSystem and PerceptionSystem have registered their own components: three Conditions and four Actions, all five of the perception- and pathing-aware ones reading straight from the process-global systems rather than through an opaque user pointer, because nothing beyond calling the registration function once is needed for a composition root to get them.

Events reuse the animation-notify seam

OnSeeTarget and the built-in FireEvent action both reach a graph through exactly the seam animation notifies already use, and there is no second wire on purpose — two mechanisms for “native code raised a gameplay event” would drift apart from each other over time. PerceptionSystem::NotifyFn and BtSystem::NotifyFn are byte-for-byte the same function-pointer signature AnimNotifyFn already declares, and both composition roots install the identical method they already had installed for animation — its body was never anim-specific.

The seam carries no payload. It is an entity and an event name, nothing else, all the way down to the C# router, so OnSeeTarget cannot itself say which entity was seen — that is why GetSynapsePerception exists as a separate query: the event says something happened, and the query says what. OnSeeTarget fires exactly once per acquisition, on the tick canSeeTarget flips from false to true, and never again while it stays true.

Authored in the editor: a tree, not a canvas

There is no node canvas for behaviour trees. The .ocbt tab is a tree view beside a parameter panel, and reparenting a node is an “Attach to” combo box rather than a drag onto another row — matching the rest of this editor's own convention, since there is no drag-and-drop for a structural edit anywhere in it. The four structural edits (add / delete / reparent / reorder siblings) are free functions, not tab methods, specifically so a headless test can drive them without ever including imgui.h or opening a window — the same split the node-graph editor already uses for the identical reason.

Every edit rebuilds the node array in pre-order so the format's “parents before children” invariant holds by construction rather than by each edit separately remembering to preserve it, and undo is a 200-deep stack of whole-tree snapshots, not command objects — cheap enough for a tree this small that the bookkeeping an undoable-command layer would need was not worth adding. Save simply refuses if the current tree fails to valid(), and a tab with unsaved edits keeps them if the file changes on disk out from under it rather than silently reloading and discarding what the author typed.

How it joins the scene with no ABI bump

Every Synapse component is registered dynamically, at each composition root, through the same World::registerComponent path a project's own C# components use — not through Components.hpp, not through scene_abi.h, and not through the fixed built-in component count. Adding CSynapseAgent, CSynapsePerception and CSynapseBehavior required no scene ABI version bump at all.

The dependency direction is disciplined in both ways at once. Synapse asks the host for two things it structurally cannot know on its own — who the perception target is, and where a fired event should go — through function pointers declared in Synapse's own headers. The host asks Synapse for agent and perception state back through two relays in framework_abi.h that a composition root fills in, which is what lets GetSynapseTarget and GetSynapsePerception read live state from a graph. Only a composition root, which already links both sides, ever sees the whole picture; everything below it stays testable alone.

What is not built

Stated together, so absence reads as a documented boundary rather than an oversight: no local avoidance, so agents in a doorway resolve through visible Jolt jitter, not steering around each other. No off-mesh links, so no jumping, ladders, or dropped ledges, and no second storey. No runtime nav baking — a level with no .ocnav beside it has no navigation, and an agent given a goal there simply waits, which is treated as a normal state, not an error. No hearing or smell, only sight. No blackboard and no interrupts in the behaviour tree, as above. No node canvas in the .ocbt editor, only a tree view and a parameter panel. And one perception target for the entire system, resolved once per tick rather than once per agent, so factions or per-agent targets need a real change rather than a setting.

    fmt::OcBtNode root; root.kind = fmt::OcBtNodeKind::Selector; root.parent = fmt::kOcBtNoParent;
    t.nodes.push_back(root);
