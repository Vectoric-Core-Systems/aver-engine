Aver Node

Gameplay with no C# at all

A graph file is not a script a component points at — it is the class asset, registered through the same three calls a C# class goes through. It compiles straight to IL, so a shipped game never needs a C# compiler on the player’s machine.

A graph is a class

One top-level record turns a plain graph into a spawnable class: CLASS AN_Orbiter Actor. That is the whole mechanism. There is no component that references a graph, no wrapper type, no registration step you write by hand — the .ocgraph file is the class asset, the same way a Blueprint asset is a class rather than a script attached to one.

It is not a parallel system either. HostBridge registers a graph class through the identical aver_fw_class_declare → aver_fw_class_set_flags(Managed) → aver_fw_class_seal sequence a C# [AverClass] type goes through, into one flat registry. A level placement naming a graph class and one naming a C# class are the same kind of placement; nothing downstream can tell which it got.

The record carries the rest of what a class needs as optional attributes — mesh=, material=, view=firstperson|thirdperson, and, on a GameMode, pawn= with controller=. Those last two are required together and warn when only one is given, because begin-play spawns and possesses the pair — and without possession the camera follows nothing, so the level renders from a default camera however loudly the character asks for first person.

Two shapes, decided by one record

A graph is exactly one of two things, and the decision is made once, from whether the file contains any ENTRY record at all.

No ENTRY makes it a pure dataflow graph: PARAMs in, up to three OUT floats out, pulled fresh every tick with no memory between calls. One or more makes it event-driven — walked from OnStart, OnTick, or any named event, with variables that persist across ticks. Only this second shape can declare a CLASS.

The two never mix in one file, and that is enforced rather than merely advised: the dataflow compiler visits every node in the graph during its topological pass, whether or not that node feeds an OUT. So an exec-only node such as Spawn or SetVar breaks a dataflow graph by existing in the file, not by being reached. That is a compile error naming the node, which is the point — the alternative is a node that silently never runs.

A third answer: DOMAIN material

Everything on this page is one answer to an optional second line a .ocgraph file can carry, DOMAIN <name>. No line at all, which is every graph on this page and every graph written before 0.4, means gameplay — the shape above, compiled straight to IL. DOMAIN material means something else entirely: nodes that shade a surface, compiled by a separate C++ compiler straight to HLSL, with no CLASS and no ENTRY at all. A name this build does not recognise — DOMAIN sound, say — is deliberately read as neither: “not mine,” skipped by every consumer, rather than silently falling back to gameplay and compiling a graph whose own author said it wasn’t one.

The two domains share a file format and an editor, and nothing else — a different compiler, a different node vocabulary, and sixteen node names that exist in both with different pins. See Materials, wired instead of written for that half of the story.

Straight to IL, never through C#

GraphCompiler emits CLR IL directly, through System.Reflection.Emit. There is no graph → C# source → Roslyn step anywhere in the pipeline, and no collectible load context involved.

The consequence is the one that matters for shipping: a player’s machine never needs a C# compiler. It needs this IL emitter, which is already linked in. A project built entirely from graphs contains no .cs file, is never told it needs a .csproj, and has nothing to compile at install time. The engine ships a playable example of exactly that — the First Person template: a character, a viewmodel, three scorable targets, a game mode and a controller, in five graphs and one map.

Compilation happens inside GraphHost.Load(), the first time a graph is loaded — which, for a class, means every time an instance is spawned.

PARAM versus VAR

They look alike and are not interchangeable. A PARAM is an input the host supplies on every call — the entity id, the frame delta — and is read-only to the graph. A VAR is the instance’s own memory: declared in the file, written with SetVar, read with GetVar, and it survives from one tick to the next.

Variables are declared in the editor now, which sounds small and was not. Validation rejects a graph addressing an undeclared variable, and until 0.3 nothing in the editor could declare one — so dragging SetVar out of the palette produced a graph that could not compile, with no way to fix it from inside the editor. A Variables panel now declares, renames, retypes and deletes them, and a rename offers to rewrite every node addressing the old name rather than orphaning them.

One exec output, many exec inputs

An exec output drives at most one link. An exec input accepts many. That asymmetry is the rule most likely to surprise someone arriving from a node editor where any pin fans out freely, and it is deliberate: execution order in a graph is a sequence, and a pin that forked would make it an unordered set.

Sequence is the fan-out primitive. When one event has to do three things in a defined order, that is what expresses it. Several branches converging back onto one node need nothing special — the inputs already accept that.

The traps that bite first

One explicit PIN record suppresses every default pin on that node, not only the one it replaced. The rule is “if this node has any explicit pin at all, add no defaults” — so a node type whose defaults are seven pins, given one hand-written PIN line, ends up with exactly one. The other six do not quietly reappear. A hand-written graph therefore spells out all of a node’s pins or none of them.

A missing input pin is now refused by name. It used to be that omitting one left the emitter asking for a pin that no longer existed, and both compilers produced IL the runtime rejected — surfacing as “Common Language Runtime detected an invalid program”, naming neither the node nor the pin. An unwired pin still defaults to zero; an absent one is now an error that says which node and which pin.

Boolean combinators and the rest of the comparisons are ordinary value nodes, not nested Branches. And, Or, Xor and Not sit in the same Logic category as Compare, which is still a strict a > b and nothing more — Greater, GreaterEqual, Less, LessEqual, Equal and NotEqual cover the rest under names a reader looks for first. A clamp is one Clamp node in Math, next to Min and Max, not Compare feeding Select. The trap that is still real: Equal/NotEqual compare floats exactly, with no epsilon, so a graph comparing computed values should subtract, Abs, and Less against its own tolerance instead.

What it cannot do yet

No 2D HUD. Nothing in the vocabulary draws text or 2D, so a graph-only game’s score can be read from the Output Log and nowhere else. The C# HUD surface exists; no node reaches it.

Firing is level-triggered. Hold a key wired to an action and it fires every tick unless the graph implements its own cooldown. The edge-triggered “pressed this frame” call exists at the ABI — again, no node reaches it yet.

Both are listed in the release notes as known issues rather than described as design. The bar for this system is Blueprint parity: if wiring something needs C#, that counts as a missing node rather than as the intended division of labour.

.ocgraph — a class with no logic, and one with
OCGRAPH 1
# THE VIEWMODEL. A mesh, parented to the camera, and nothing else -- this graph
# has no logic at all and does not tick.
#
# `mesh=` on the CLASS line is enough on its own. There is no OnStart here because
# there is nothing to do once the archetype carries the mesh: ClassBuilder applies
# mesh= and material= at spawn, so the instance has both before a first tick would
# have run.
NAME FPGun
DESCRIPTION The first-person viewmodel, parented to the camera by AN_FPCharacter.

CLASS AN_FPGun Actor mesh=Meshes/Blaster.ocmesh material=M_Gun

# ---------------------------------------------------------------------------
# A graph with logic. VAR is the instance's own memory; ENTRY names an event;
# LINK joins a pin to a pin. Any explicit PIN record suppresses ALL of a node's
# defaults, so a hand-written node lists every pin or none.

VAR   hits int 0
ENTRY begin  OnStart
ENTRY step   OnTick

NODE  begin  SetVar var=hits
NODE  step   GetVar var=hits
LINK  step.value begin.value
The records a graph file is made of
RecordWhat it declares
CLASSTurns the file into a spawnable class asset. Optional mesh=, material=, view=, and pawn= + controller= on a GameMode
PARAMAn input the host supplies each call — entity id, frame delta. Read-only
VARThe instance’s own memory, surviving between ticks. Must be declared to be addressed
ENTRYAn event this graph answers — OnStart, OnTick, or a named one. Its presence picks the compiler
NODEOne node, its type, and its type-specific attributes
PINAn explicit pin. Any one of these suppresses every default pin on that node
LINKJoins an output pin to an input pin
OUTA dataflow graph’s result — up to three floats. Only on a graph with no ENTRY
